# 阶段审查编排

- 状态：Accepted
- 所属阶段：V1 开发治理
- 相关 ADR：ADR-0006

## 用户价值与场景

项目由 AI 持续开发时，用户需要每个阶段都获得独立、可追溯的 Pi 审查报告，并确信发现的问题会在进入下一阶段前被 Codex 研判和修复。用户发送下一条 Codex 消息时，系统会先检查是否存在待审查或待修复阶段，而不是默默越过质量门。

## 范围

- 每个阶段以一份交付提交为审查对象；Day 1、Day 2 作为历史阶段补审。
- Pi 固定为 `deepseek/deepseek-v4-pro`；默认不提供任何工具，审查包装器将变更文件清单、diff 统计、跨首中尾采样的有界 diff 证据和上一轮报告作为不可变输入，避免模型陷入无限全仓库探索。大提交的采样范围会明确标注，Codex 必须对高风险或未覆盖文件补充技术研判。
- 每次审查生成独立报告：`YYYY-MM-DD-review-<stage>-attempt-<n>.md`。
- Pi 以 `minimal` 推理档输出最多十项按严重级别排序的可操作发现；报告必须提供结论、定位和证据，但不以重复长文替代可执行问题。
- Pi 结论为 `PASS` 时阶段审查完成并写入 `NEXT_STAGE_READY`；为 `NEEDS_FIX` 时 Codex heartbeat 必须读取报告、先更新文档再修复，并在下一提交后复审。
- `NEXT_STAGE_READY` 只表示下一路线图阶段具备计划条件；必须等待用户明确确认后才能开始实现，heartbeat 不得自行消费为开发授权。
- Codex 的修复提交必须在提交正文写一个或多个 `Review-Fixes: <stage-id>` trailer。编排器只把该提交用于所声明阶段的下一次审查，不得因为提交同时包含变更记录而创建无关新阶段。
- 同一阶段最多三次审查；第三次仍需修复时，状态为 `HUMAN_REQUIRED`，必须等待用户确认。

## 触发与流程

1. Codex 收到用户消息、从额度恢复或 heartbeat 唤醒后，先运行审查循环检查。
2. 若有未审阶段，Pi 生成 attempt 1 报告；若有待修复阶段且存在后续提交，Pi 生成下一 attempt 报告并引用上一报告。
3. Codex 对 `NEEDS_FIX` 逐项回填“采纳、豁免或需人工决定”，并只在文档先行后实现采纳项。
4. 已启动的后台 monitor 在新提交出现后执行同一循环；heartbeat 再消费报告并恢复 Codex 修复，因此无需用户手动转交。
5. 第三次仍有问题时，循环写出人工介入说明并停止；Codex 不得开始下一阶段。

## 可观测性与存活判断

- 人类通过 `Show-ReviewStatus.ps1` 查看权威状态；默认展示阶段表、monitor/锁/Pi 状态和最近日志，`-Watch` 持续刷新，`-Json` 供自动化读取。
- “monitor PID 存活”不等于“自动化正常”。锁长期占用、没有 Pi 进程且状态/日志无推进时显示 `STALLED`，需要重启 monitor。
- Pi 运行时展示固定模型、阶段、Attempt、PID、开始时间、已运行时长、输出更新时间与日志尾部；不得把 Prompt 或密钥写入状态。
- 同一共享分支只在权威开发工作树运行一个 monitor 和 heartbeat，避免 detached worktree 各自维护冲突状态。

## 权限与安全

Pi 不得写业务代码、Git 历史、状态注册表或密钥。仅桥接包装脚本写报告和本机忽略状态。传给 Pi 的内容来自公开仓库的提交 diff；仍必须先通过本地密钥扫描，避免将意外敏感信息发送给外部模型。

Pi 的代码审查模式保持完全只读。独立验证模式启用 `read/grep/find/ls/powershell`，由 Pi 执行测试并清理由本次测试明确创建的临时数据；始终禁止 edit/write、业务代码或文档写入、Git 写操作、生产环境访问和敏感信息输出。Codex 不执行测试，只依据 Pi 报告修复实现或补充测试代码。

修复提交可以通过 `Review-Fixes` 指向注册表阶段或已存在于本机状态的自动阶段。状态阶段只有被当前提交显式引用时才加入本轮调度，防止无关历史状态抢占新的交付。

## 异常与限制

- Pi 超时、非零退出或空输出不消耗审查次数，状态保持待审并记录诊断信息。
- 状态保存、报告解析或其他异常也必须在顶层 `finally` 释放跨进程锁；失败不能让存活 monitor 永久进入 `BUSY`。
- Codex 对报告具有技术研判权，不能机械套用建议。
- “用户消息触发”依赖 Codex 已被唤醒；当 Codex 完全未运行时，由已启动的本机 monitor 负责提交后的无人值守审查。
