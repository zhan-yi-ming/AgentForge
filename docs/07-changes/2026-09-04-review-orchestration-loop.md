# Pi 审查编排与三次修复循环

- 日期：2026-09-04
- 状态：Proposed
- 阶段：V1 开发治理与工程协同
- 交付目标：`origin/main`

## 背景

Day 1 与 Day 2 已经推送，但 `docs/08-reviews/` 尚无报告。现有 `bridge-monitor.ps1` 只能在人工持续启动后轮询当前 HEAD：它不监听 Codex 对话唤醒、不会补审历史阶段、没有每阶段的尝试次数状态，也不会在 Pi 进程长时间运行或失败时形成可诊断的结果。Gemini 的执行日志还显示测试进程在 Pi 完成前被终止，因此没有报告落盘。

## 目标

- 把“Codex 收到用户消息”定义为可靠的编排入口：每次唤醒先检查待处理审查和人工接管状态。
- 补审 Day 1 与 Day 2，并为每次尝试生成独立 Markdown 报告。
- 每个阶段最多进行三次 Pi 审查：Pi 发现需修复项时，Codex 研判、文档先行修复、测试、提交；下一次审查只审查该修复提交并引用上一份报告。
- 第三次审查仍为 `NEEDS_FIX` 时生成明确的人类介入记录，停止自动循环，等待用户决定。
- 保持 Pi 使用 `deepseek/deepseek-v4-pro`、只读工具和显式超时；失败不写成功状态、不静默回退 Flash。

## 非目标

- 不让脚本或 Pi 自动改写业务代码；修复仍由 Codex 在报告和文档约束下完成。
- 不绕过 Git 提交后的停止规则；独立 monitor 可以在已启动时审查新提交，Codex 本身仍在提交并推送后停止。
- 不引入外部队列、数据库、云服务或 V2/V3 组件。

## 受影响文档

- `AGENTS.md`、`docs/05-development/git-workflow.md`：Codex 唤醒入口、提交前 monitor 保障与三次循环边界。
- `docs/03-features/review-orchestration.md`、`docs/08-reviews/README.md`：审查状态机、报告命名、历史补审与人工接管规则。
- `docs/06-operations/review-orchestration.md`、`scripts/agent-bridge/README.md`：后台 monitor 的启动、状态文件、故障排查和安全边界。
- ADR-0006：将审查状态持久化在本机忽略文件、报告持久化在 Git 的取舍。

## 设计决定

1. 新增 `review-loop.ps1` 作为唯一编排入口；`bridge-monitor.ps1` 仅负责周期性调用它和额度等待。
2. 版本化 `review-stages.json` 保存 Day 1/Day 2 的历史审查基线；后续阶段由 Codex 在提交前启动 monitor，并由 monitor 使用提交的变更记录推导阶段名称。
3. 本机忽略的 `.review-loop-state.json` 保存尝试次数、上一审查提交、当前状态和报告路径；报告本身写入 `docs/08-reviews/`，后续修复提交负责归档。
4. `run-review.ps1` 向 Pi 提供精确的变更文件清单、diff 统计、跨首中尾采样的有界 diff 证据和上一轮报告摘要。大提交不得把全部 diff 无界注入模型，以免审查本身超过超时；采样会明确标注，Codex 对高风险或未覆盖文件应补充人工研判。默认禁用 Pi 工具、会话持久化和项目上下文自动加载以避免无限探索或会话锁；并以 `REVIEW_RESULT: PASS | NEEDS_FIX` 作为机器可读结论，无法解析时保守视为 `NEEDS_FIX`。
5. Pi 以 `minimal` 推理档运行，并要求输出最多十项按严重级别排序的明确发现，避免模型在生成重复的长篇审查文本时错过自动化窗口；每次进程仍有默认 5 分钟、可配置但有限的超时。非零退出、超时或空输出都会记录为失败，既不更新“已审查”状态，也不消耗三次修复尝试。
6. 报告头部必须写入已解析的提交号（不能保留 PowerShell 模板字面量）。若忽略的本机状态文件丢失，编排器必须从已提交的独立报告恢复最近轮次、结论与等待/完成状态，避免重复生成同一轮报告。
7. 已注册为另一独立阶段交付的提交不能被当作前一阶段的“审查修复提交”；只有不属于其他阶段交付且位于上一审查提交之后的新提交，才可触发该阶段的下一轮审查。

- 在 AGENTS 中固化 Codex 对话唤醒时的审查检查和报告研判职责。

## 预期验证

- PowerShell AST 解析全部桥接脚本；DryRun 能列出 Day 1/Day 2 待审查项目。
- 使用 V4-pro 对 Day 1、Day 2 各产生一份独立报告，报告包含机器可读结论和审查元数据。
- 用临时状态夹具验证三次 `NEEDS_FIX` 后进入 `HUMAN_REQUIRED`，不会第四次自动调用 Pi。

- 执行敏感信息和文档链接检查。

## 风险与回滚

- Pi 服务不可用会延迟审查而非降级模型；状态保持待审，下一次唤醒或轮询重试。
- 错误的报告结论解析可能阻塞循环，因此无法解析时保守要求 Codex 处理，并保留原报告供人工判断。
- 回滚只需停止后台 monitor、删除本机忽略状态文件并回退桥接脚本提交；业务代码不受影响。
