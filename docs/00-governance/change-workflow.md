# 标准变更流程

- 状态：Accepted

## 1. 建立上下文

先执行 Git preflight：fetch 目标远端，确认当前分支和 base commit，列出用户已有 staged / unstaged / untracked 文件；不得到提交前才处理过期基线或 detached HEAD。

按 `efficient-validation.md` 建立任务上下文包：阅读文档地图、当前变更、受影响功能/API/架构/ADR、直接调用方和相关测试。只有边界变化、冲突、失败或影响未知时扩大阅读，不机械加载无关历史。

V2/V3 Node 还必须读取 `v2-v3-node-development-protocol.md` 与路线图当前 Node，完成 Node Start Gate 并等待用户确认。当前 Node 的开发顺序与 Scope 以节点路线图为唯一来源。

## 2. 写变更记录草稿

在 `docs/07-changes/` 创建记录，至少先填背景、目标、范围、非目标、计划修改的文档和实现。此时状态为 `Proposed`。

## 3. 先写目标状态文档

根据变更类型更新功能、API、架构、数据、开发或运维文档。文档必须把关键取舍讲清楚；复杂设计先新增 ADR。

## 4. 实现

只实现已经写进文档的范围。发现设计需要变化时，暂停实现，先回到步骤 2 或 3 更新文档。

## 5. 验证

Codex 分别评估风险等级与影响范围，并运行 `scripts/validation/plan-change-gates.ps1` 取得最低门禁建议。L0/L1/L2/L3 决定 Review 和失败类型覆盖，实际触达的 Docs/Web/Core API/Agent Service/TLS/跨服务范围决定测试套件。L3 不自动等于全仓；Release Gate、共享全仓变化或影响无法收敛才执行全仓回归。强制升级规则以 `efficient-validation.md` 为准。

Codex 亲自执行选定门禁并清理由本次测试创建的临时数据。失败时先建立可重复信号，再按文档先行和 TDD 修复。同一任务内，相关源码、配置、依赖、base 和契约未变化的已通过结果可以复用；任一相关输入变化、失败或 Review 指向该范围时必须重跑。跨任务旧缓存、历史报告和模型文字不能作为证据。

## 6. 回填证据

Codex 把实际文件、接口、迁移、测试命令、退出码、数量、失败/跳过、清理结果和偏离原计划之处写回变更记录。将相关文档状态更新为 `Implemented`。

## 7. 风险匹配的 Pi 只读审核

L0/L1 默认不调用 Pi；L2 在相关测试后执行 Diff Review；L3、开发节点结束、连续 5 次 L0/L1 或 Release Gate 执行 Milestone Review。节点/累计触发扩大的是方向与 Scope 审计，机器测试仍由累计或当前变更的真实影响范围决定；只有影响无法可靠还原时升级全仓。Pi 不运行测试、不修改文件、不启动 monitor，也不自动推进阶段。连接方式见 `../06-operations/pi-review-connection.md`。

只有用户针对本次变更明确豁免时才可跳过；豁免原因必须写入变更记录。Pi 登录、额度、启动器、模型或环境失败时立即请用户处理，不得全盘搜索、安装尝试、Flash 降级或循环重试。

## 8. 创建阶段提交

AI 在确认文档已回填、验证结果真实且暂存区只包含本阶段变更后，创建一个真实、可读的 Git 提交。提交信息应表达本阶段的完整意图，不能把下一阶段工作混入当前提交。目标分支与远端基线应已在步骤 1 确认。

V2/V3 Node 在创建提交前必须重新核对节点协议要点、当前 Roadmap Node、任务上下文包和最终 diff，输出 Node Close Gate；只有 Gate 为 YES 才能提交。提交、推送和远程核验后停止，禁止自动进入下一 Node。

## 9. 推送当前提交

提交成功后不得再修改该变更；先把提交推送到事先确认的远程分支，并用远程引用核验 commit。禁止 force push，远程存在意外历史时立即停止并报告。

提交信息标题表达阶段意图，正文至少概括文档、行为 / 接口、数据迁移、安全影响、验证结果和已知限制。变更记录提供详细上下文，Git 远程引用提供实际 commit / push 事实，不在仓库文件内伪造无法自指的 commit hash。

## 10. 推送后检查点

推送核验成功后，当前变更关闭并汇报：

1. 本阶段已经完成的内容。
2. 已运行验证、未通过或未运行项及原因。
3. 用户可以介入的事项，并明确哪些是必需、哪些只是建议。
4. 下一阶段的目标、文档先行项、实现步骤、验证方式和明确非目标。

V2/V3 下一 Node 即使已在路线图中也必须等待用户新的明确确认。用户已经明确授权并排序的独立非 Node 后续任务，可在前置变更远端核验后创建新的变更记录并继续；不得把两个主题混进同一提交。若推送失败必须停下，不能开始后续任务。

## 小改动如何处理

拼写修正或同一主题内的轻微整理，可以更新当前变更记录，不必机械地一字一记录。但只要行为、接口、配置、数据或目录发生变化，就必须有对应证据。

同一大版本或同一阶段内发现的非阻断问题采用批量闭环：Codex 一次性完成相关文档与整批实现，再统一审查和全量测试。不要为单个轻微问题重复创建独立变更记录或提交循环。只有安全漏洞、数据破坏风险、架构级决策或阻塞后续开发的问题才立即单独中断处理。

同主题轻微变更仍在当前记录中逐项留下范围和验证证据，并增加 L0/L1 累计计数。未命中累计或节点触发条件时可以不做 Pi；纯文档变更按实际范围执行文档一致性、路径、格式和敏感信息检查，不虚构不适用的代码测试。

每次完成修改后必须报告：风险等级、修改范围、可能影响、本次验证、未执行项及原因。L2/L3 不得为了节省时间主动降级门禁；影响范围无法确认时自动升级为 L2。

Pi 仅恢复为提交前一次性只读代码审核；Codex 仍是唯一测试执行者。旧 monitor、validation 和自动阶段推进保持停用。详见 `../06-operations/pi-review-connection.md`。
