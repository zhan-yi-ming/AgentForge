# 标准变更流程

- 状态：Accepted

## 1. 建立上下文

阅读产品范围、架构、相关功能、API、ADR 和最近变更。确认当前阶段允许做什么，防止提前引入 V2/V3 能力。

## 2. 写变更记录草稿

在 `docs/07-changes/` 创建记录，至少先填背景、目标、范围、非目标、计划修改的文档和实现。此时状态为 `Proposed`。

## 3. 先写目标状态文档

根据变更类型更新功能、API、架构、数据、开发或运维文档。文档必须把关键取舍讲清楚；复杂设计先新增 ADR。

## 4. 实现

只实现已经写进文档的范围。发现设计需要变化时，暂停实现，先回到步骤 2 或 3 更新文档。

## 5. 验证

按风险运行格式检查、单元测试、集成测试、构建和必要的人工检查。失败必须修复或明确记录为已知限制。

## 6. 回填证据

把实际文件、接口、迁移、测试命令、测试结果和偏离原计划之处写回变更记录。将相关文档状态更新为 `Implemented`。

## 7. 创建阶段提交

AI 在确认文档已回填、验证结果真实且工作区只包含本阶段变更后，创建一个真实、可读的 Git 提交。提交信息应表达本阶段的完整意图，不能把下一阶段工作混入当前提交。

## 8. 推送当前提交

提交成功后不得再修改文件，也不得运行下一阶段命令；唯一允许的交付动作是把刚创建的提交推送到事先确认的远程分支，并用远程引用核验 commit。禁止 force push，远程存在意外历史时立即停止并报告。

提交信息标题表达阶段意图，正文至少概括文档、行为 / 接口、数据迁移、安全影响、验证结果和已知限制。变更记录提供详细上下文，Git 远程引用提供实际 commit / push 事实，不在仓库文件内伪造无法自指的 commit hash。

## 9. 推送后强制中断

推送核验成功后，AI 必须立即停止开发。最终汇报包含：

1. 本阶段已经完成的内容。
2. 已运行验证、未通过或未运行项及原因。
3. 用户可以介入的事项，并明确哪些是必需、哪些只是建议。
4. 下一阶段的目标、文档先行项、实现步骤、验证方式和明确非目标。

只有用户明确确认下一阶段计划后，AI 才能开始下一阶段。若提交成功但推送失败，也必须停下并报告，不得借机开始新实现。若用户提出修改意见，先更新计划；确认前不实现。

## 小改动如何处理

拼写修正或同一主题内的轻微整理，可以更新当前变更记录，不必机械地一字一记录。但只要行为、接口、配置、数据或目录发生变化，就必须有对应证据。
