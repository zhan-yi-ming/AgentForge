# 文档先行制度

- 状态：Accepted
- 适用范围：整个仓库，包括代码、配置、脚本、数据库、CI 和文档自身
- 规则来源：根目录 `AGENTS.md`

## 目的

AgentForge 全程由 AI 辅助建设。AI 的会话记忆不应成为项目唯一知识来源，因此仓库内文档必须承担“可检索、可解释、可追溯”的长期记忆职责。用户和后续 AI 都应能只通过仓库理解当前状态和历史理由。

## 核心规则

任何增、删、改必须按“变更记录 → 目标文档 → 实现 → 验证回填”的顺序执行。即使只是配置项、字段、异常处理或文件移动，也不能跳过。

## 变更类型与必改文档

| 变更类型 | 必须先更新 | 视情况更新 |
| --- | --- | --- |
| 新功能或行为变化 | `03-features/`、`07-changes/` | `04-api/`、`01-product/` |
| API 增删改 | `04-api/`、`07-changes/` | 功能文档、ADR |
| 数据表、字段、索引变化 | `02-architecture/data-architecture.md`、`07-changes/` | 功能文档、ADR、运维文档 |
| 模块边界、依赖或技术选型变化 | ADR、对应架构文档、`07-changes/` | 产品路线、开发文档 |
| 配置、运行方式或基础设施变化 | `05-development/` 或 `06-operations/`、`07-changes/` | ADR |
| Bug 修复 | 受影响功能文档、`07-changes/` | API、测试策略、排错文档 |
| 删除或废弃 | 原文档标明 Deprecated、`07-changes/` | ADR、迁移说明 |

## 功能文档的最小内容

每个功能文档至少回答：

1. 谁在什么场景下使用它。
2. 正常请求从哪里进入、经过哪里、在哪里校验、在哪里落库。
3. 暴露哪些接口，使用哪些关键数据。
4. 哪些权限或人工确认保护它。
5. 失败时返回什么、如何排查。
6. 如何测试，当前有哪些未实现或限制。

## 架构决策何时写 ADR

出现以下任一情况必须写 ADR：

- 引入或移除框架、中间件、外部服务。
- 改变模块拆分、服务边界或依赖方向。
- 改变认证、授权、审批、审计等安全模型。
- 改变持久化策略、主键策略、迁移方式或跨模块一致性。
- 存在两个以上合理方案，且选择会影响后续维护成本。

ADR 一经 Accepted 不直接覆写历史结论。新决策通过新的 ADR 取代旧决策，并互相链接。

## 可追溯性要求

- 变更记录链接受影响文档和实现位置。
- 功能文档链接相关 API、数据模型和 ADR。
- 实现中的公共接口、迁移文件和配置命名应能在文档中被搜索到。
- 测试结果必须记录实际执行命令；未运行也要说明原因，不能写成通过。

## 例外

没有“无文档例外”。紧急修复可以先写一份短记录，说明现象、风险和临时方案，然后立即修复；修复后再补齐根因和长期方案。
