# Git 工作流

- 状态：Accepted

## 原则

- 每个阶段保留真实、可读的提交记录。
- 一次提交尽量表达一个完整意图，并同时包含对应文档、实现和测试。
- AI 在阶段实现和验证完成后负责创建提交。
- 提交成功即进入强制检查点：AI 必须停止开发，等待用户确认下一阶段计划。

## 建议检查顺序

1. 阅读当前 `docs/07-changes/` 记录。
2. 运行 `git status --short`。
3. 分别阅读文档、迁移、公共接口和测试的 diff。
4. 重新运行关键验证，确认记录与实际结果一致。
5. AI 创建提交，例如 `feat(core-api): bootstrap users and projects`。
6. AI 汇报完成内容、验证与限制、非必需的用户介入项和下一阶段计划。
7. 用户明确确认后，AI 才进入下一阶段。

## 提交后汇报格式

- **已完成**：用户可以从文档和代码核对的结果。
- **验证与限制**：实际执行结果，不能把跳过项写成通过。
- **需要用户介入**：先写“必需”或“非必需”；没有必需项时要明确说明。
- **下一阶段计划**：目标、先更新的文档、实现顺序、验收条件和非目标。
- **等待确认**：清楚说明在用户确认前不会继续开发。

## 禁止

- 不提交 `.env`、密钥、IDE 私有配置、日志、数据库卷或构建产物。
- 不用强制重写共享历史掩盖错误；使用新的修复提交保留证据。
- 不把多个阶段堆在一个巨大提交中。
