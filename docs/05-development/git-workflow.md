# Git 工作流

- 状态：Accepted

## 原则

- 每个阶段保留真实、可读的提交记录。
- 一次提交尽量表达一个完整意图，并同时包含对应文档、实现和测试。
- AI 在阶段实现和验证完成后负责创建提交。
- 远程仓库为 `git@github.com:zhan-yi-ming/AgentForge.git`，默认共享分支为 `main`。
- 提交成功后不再改文件，只推送并核验当前提交；推送后进入强制检查点。
- 不把 GitHub 当作密钥存储，所有提交遵守 `../00-governance/public-repository-security.md`。

## 建议检查顺序

1. 阅读当前 `docs/07-changes/` 记录。
2. 运行 `git status --short`。
3. 分别阅读文档、迁移、公共接口和测试的 diff。
4. 重新运行关键验证，确认记录与实际结果一致。
5. AI 创建提交，例如 `feat(core-api): add authenticated wiki and task workflows`；正文详细列出文档、接口、迁移、安全、测试和限制。
6. AI 推送到已确认分支并核对远程 commit；禁止 force push。
7. 阶段审查（Pi Agent）：由 Pi Agent (DeepSeek) 自动或手动拉起只读审查，对比阶段提交与 diff，生成 `docs/08-reviews/YYYY-MM-DD-review-day-<X>.md` 审查报告。
8. Codex 评估与修复：Codex 读取审查报告，评估 Issue 并实施必要修复与测试回填；若遇 5 小时限额则等待调度器倒计时唤醒后处理。
9. AI 汇报完成内容、审查结果、验证与限制、用户介入项和下一阶段计划。
10. 用户明确确认后，AI 才进入下一阶段。

## 提交后汇报格式

- **已完成**：用户可以从文档和代码核对的结果。
- **验证与限制**：实际执行结果，不能把跳过项写成通过。
- **需要用户介入**：先写“必需”或“非必需”；没有必需项时要明确说明。
- **下一阶段计划**：目标、先更新的文档、实现顺序、验收条件和非目标。
- **等待确认**：清楚说明在用户确认前不会继续开发。

## 禁止

- 不提交 `.env`、密钥、IDE 私有配置、日志、数据库卷或构建产物。
- 不用强制重写共享历史掩盖错误；使用新的修复提交保留证据。
- 不把多个阶段堆在一个巨大提交中。
- 不在提交和对应推送之间产生额外文件修改。
